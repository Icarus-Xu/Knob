# 项目策略备忘录

## 决策1：接口优先级
- **只用官方接口**：车机厂商官方 SDK（bydauto-openapi.jar）提供的稳定接口
- **非官方的底层直写接口已放弃**：实车实测该调用方式抛 `NoSuchMethodException`（方法签名与运行时 SDK 对不上，见 `验证结论.md` 结论 7）。对应的开关与 featureId 直写代码已于 2026-08-28 从 `CarControl.kt` 移除。

## 决策2：调试顺序（减少签名次数）
车机厂商签名版每次修改都要重新上传签名，测试成本高。
因此调试顺序应尽量**先本地、后签名**：

### 建议的调试阶段划分
- **阶段A（无需签名）**：蓝牙通路
  - ESP32 BLE HID 键盘 + 车机识别 + 无障碍服务捕获按键 → 日志显示收到哪个键
  - 纯本地可反复测试，不依赖车机厂商签名
- **阶段B（无需签名）**：App 收到按键后的动作映射框架
  - 按键 → 触发某动作（先映射成日志/UI，不实际调车控）
- **阶段C（需签名）**：App 收到按键 → 调 BYDAUTO 车控接口
  - 这一步才需要车机厂商签名版

### 目标
先打通 A、B 阶段（本地调稳），最后一次性签名测试 C 阶段，
大幅减少"上传→签名→装车"的迭代次数。

## 决策3：车控逻辑迁移到插件（壳 + DEX 热加载）
- 目标：壳只签名一次（车机厂商），后续所有代码更新通过下发 plugin.dex，无需重签
- 架构：壳（加载器+UI+框架） ←DexClassLoader→ 插件（全部车控/业务逻辑）
- 关键机制：插件 DEX 运行在壳进程（壳 UID），继承车机厂商签名权限，能调 BYDAUTO
- 接口形态：严格四功能域（onCommand/onQuery/onEvent/onPush），连 UI 容器的绑定/解绑都走事件域（ui.bind / ui.unbind），不为它单开方法。新增功能只加路由分支，接口不变 → 壳不重签
- 当前状态：
  - 壳：api 契约 + PluginLoader + KnobApp 启动加载 + KnobActivity（左日志右插件容器），已瘦身完成
  - 插件：CarControl（车控引擎）+ PluginSelfTest（自检）+ MainPlugin（四域路由 + 自管页面栈）
  - 已产出 plugin.dex（含完整车控逻辑）
- 验证路径：壳签名版装车 → 用「选择插件」导入 plugin.dex → 验证加载 → 之后只发 DEX
